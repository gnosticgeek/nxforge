# NXForge Converter

A native Mac app (SwiftUI, macOS 26 or later) over `scripts/build_ipa_from_nsp.py --platform mac-app`: it turns one game's folder into a native Mac app ([A Mac app](../docs/development.md#a-mac-app)) without the command line. It needs only Xcode to build: the key check uses the system's CommonCrypto.

- **Convert.** Choose the game's folder (the base game, plus its update and DLC if you have them) and `prod.keys` (taken from the folder when it is there, else the default keys file from Settings). The converter checks the files against the keys in under a second: it decrypts each NCA's header with `header_key`, the title key from the NSP's ticket with `titlekek_XX` (or the key area with `key_area_key_*_XX`), and the first bytes of a section, which must read as PFS0 or RomFS. NSZ and XCZ files get the header and key checks; the build checks their data. No key value is shown, logged or stored, only key names. **Build Mac app** runs the script with `--progress json`, shows the build as one bar with the time left (from this game's last build, or other games' builds scaled by size; the step list and a filterable log are under Show details), then checks that the app's launcher is executable and that `codesign --verify --deep --strict` passes. The app goes beside the game files, or to the output folder you choose. **Switch 2 games** come as one `.nup` file or a dump folder, not NSPs, and need no keys: choose the `.nup` itself (or a folder holding one, or the dump folder) and the keys row says it is not needed. The engine's `scripts/source_info.py` reads the container's index without unpacking it, and Convert lists the base game, updates and DLC, whether NXForge has a profile for the game (without one the build guesses a profile, shown as a warning), and whether its code is ZBIC-compressed (system 22 or later, such as Ocarina of Time), which needs `zbic` in the converter's Python (Toolchain sets it up). The build folder and the app go beside the `.nup`, and a first build needs about twice the game's files plus 20 GB (Ocarina of Time's 26 GB `.nup` peaked near 76 GB, with a 35 GB app), so pick a `.nup` on a drive with room. **Preview build** (once a game has a build folder) runs the script with `--plan`: it lists which steps a build would reuse and which it would redo, with how long each took last time, and builds nothing. Once it is built, Convert clears (folder, keys, check and activity) and Builds opens on the new app; a failed build stays on Convert with its stages and log.
- **Library.** Choose a games folder (on Library, or in Settings) and the converter lists every game under it, in every folder up to 8 levels down: a folder of NSP / XCI / NSZ / XCZ files, a Switch 2 `.nup`, or a Switch 2 dump folder. Each row shows the game's own name, icon, publisher and version, read from its Control NCA with `prod.keys` (beside the game, else the default or last keys file; a few hundred KB per game, kept between scans, so the file names are only a fallback), what is there (base game, updates, DLC), its title ID and size, whether NXForge lists it as playing, booting or broken (`docs/nxforge-games.tsv`) or has a profile for it, and whether it is built and on which engine (apps are matched by the title ID in their bundle ID, wherever they were built). A filter picks not built, plays, has a profile, built on an older engine, a newer update than the build used, or needs attention. **Convert** (or a double-click) makes a game the one on Convert; tick several and **Build selected** builds them one after another, with a free-space estimate per drive first (a failed game is noted and the next one starts; stopping the build or running short of space ends the run). The build takes one game per folder, so games whose files share a folder (loose NSPs in the root, two games in one folder) are listed one by one and moved into a new folder named after them before they build (a rename on the same drive). Update or DLC files in a subfolder, which the build does not read, move beside the game in one click; the same game in two folders gets a note on each; a folder with only an update or DLC says so. The scan runs off the main thread with a Stop button; each folder listing has a 20-second limit, so a slow or sleeping share skips the folder instead of hanging, and after three folders in a row with no answer the scan stops and keeps the games it found plus last scan's for the folders it did not reach. The list is kept in `library.json` (icons in `library-icons/`) beside the settings, so it shows at once at the next start, even with the share away; it is scanned again when the games folder's drive or share mounts, when the Library opens on a list over a day old, and with **Scan again**.
- **Builds.** Every app the converter built, with the engine version it was built on: its release (`0.1.0`, or `0.1.0+3` three commits after it; a build from before the first release shows as `pre-0.1.0`, older records included), with the commit in its tooltip. The engine is the NXForge checkout the script runs from; the bundle carries no version, so each build is recorded in `~/Library/Application Support/NxNative Converter/builds.json`. **Rebuild** (the blue button when the app is on an older engine) moves the app to `app-backups/<name> (<version>, <time>).app` in its folder (a rename, no space taken), runs the full script into the same path (stages with unchanged inputs are reused, so a host-only engine change rebuilds the host and repacks), and puts the old app back if the build fails. **Previous builds** lists those kept copies, to open, restore or move to the Trash. **Keep this build** (a switch in the detail panel, or the right-click menu) marks an app that plays well: it shows a lock instead of the "older" badge, Rebuild all passes it by, and a rebuild asks first; the new build is not kept. One build per game folder runs at a time (`.nxnative-converter.lock`).
- **Toolchain.** Each tool the script needs, found as the script finds it: its own `TOOL_PATHS` first, then `PATH`, so a tick means the script finds the same tool. The shader translator is started, not just found: its launcher finds .NET only through `DOTNET_ROOT`, which the converter sets to the folder of the `dotnet` the script uses. A missing tool's **Fix** runs its install command in Terminal. The engine section shows the checkout's version, **Check for updates** fetches its branch's upstream and **Update engine** fast-forwards to it; a release branch still checked out after its merge updates from `main` instead (Update engine switches to it). **Copy diagnostics** copies the findings (paths and versions, no key values).
- **Settings.** Appearance, a notification when a build ends, opening the app after a build, the signing identity (`--mac-sign`; ad-hoc by default), the default output folder and keys file, reusing cached stages (off deletes the stage keys in `<id>_build`, so every stage runs again), keeping previous builds (off moves the replaced app to the Trash), log detail (Detailed adds the tools' own logs to Copy log) and the game's build cache.

- **Storage.** Every game's build cache, older app copies, apps and the shared Metal cache (`~/Library/Caches/NXForge`), with sizes and each disk's free space. Caches and app copies can be deleted (permanently, so the space comes back at once). While a build runs, the converter warns below 12 GB free and stops the build below 3 GB; the finished steps are reused by the next build.

Small things: drop a game folder (or a file in it), or a `.nup`, on the window or the Dock icon to convert it; a first build needs about twice the game files' size plus 10 GB, so Convert shows the free space and warns when it is short; the Dock icon shows the build's progress; **Build** in the menu bar has Build Mac App (⌘B), Rebuild (⌘R), Rebuild All on Older Engines and Stop Build (⌘.), and ⌘O chooses a game folder. On Builds, apps on an older engine carry an "older" badge, **Rebuild all** rebuilds them one after another (a failure stops the rest), and a right-click opens, shows, rebuilds, removes from the list or moves an app to the Trash. At launch the converter fetches the engine's branch, and when it has updates shows the newest release's first change from its CHANGELOG. On Toolchain, **Set up** makes the converter's own Python (a venv in Application Support with lz4, capstone, fontTools, zstd, nsz and zbic) so it depends on no other copy; it needs the network once, for pip. The app's icon is drawn by `make_icon.swift`, and its version is the engine's release tag.

Settings are in `~/Library/Application Support/NXForge Converter/settings.json` (before 0.8.0 the folder was `NxNative Converter`; the first start moves it and leaves a link at the old name). The repository is found from the setting, then the checkout the app was built in, then `~/Developer/nxforge`, `~/nxforge`, `~/Developer/nxnative`, `~/nxnative` and similar. Python is the setting, then `~/Library/Application Support/NxNative Converter/venv`, then the checkout's `.venv`, then each `python3` on `PATH`, the first with the modules winning.

## Build

```
app/install.sh
```

builds the converter from this checkout into `~/Applications` and opens it, so Spotlight, Launchpad and the Dock find it there; run it again after pulling to update (quit the converter first). `app/bundle.sh` builds into `app/.build` instead. To work on it in Xcode, `open app/Package.swift`.

The same steps run without the window, which is how it is tested:

```
app/.build/release/NXForgeConverter --check
app/.build/release/NXForgeConverter --validate "<game folder>" "<prod.keys>"
app/.build/release/NXForgeConverter --convert "<game folder>" "<prod.keys>" [--sign "<identity>"]
app/.build/release/NXForgeConverter --convert "<game>.nup"          # a Switch 2 .nup or dump folder: no keys
app/.build/release/NXForgeConverter --rebuild "<game folder>/<game>.app" "<prod.keys>" [--sign "<identity>"]
app/.build/release/NXForgeConverter --engine "<game folder>"
app/.build/release/NXForgeConverter --verify "<game>.app"
app/.build/release/NXForgeConverter --library "/Volumes/Gaming/roms/switch" ["<prod.keys>"]   # the Library scan, printed (with keys: names and versions); nothing is moved
```

The unit tests (release names, title IDs, the settings file, the Library scan) run with `swift test --package-path app`; CI runs them, builds the bundle and starts `--check` in the `converter` job of `.github/workflows/tests.yml`.

For checking the window: `NXC_SNAPSHOT=<file.png>` saves a picture of it a few seconds after it opens, writes its window number to `<file.png>.wid` for `screencapture -l`, and quits (`NXC_PAGE=library`, `builds`, `storage` or `toolchain` for another page; Settings is its own window, opened with ⌘,; `NXC_AUTOBUILD=1` builds the chosen folder first). `NXC_SUPPORT_DIR=<folder>` keeps settings and build records there instead, to test beside a copy in use.
